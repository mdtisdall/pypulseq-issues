# Area of an oversampled arbitrary gradient counts only the raster-centre samples

**Summary**

For an oversampled arbitrary gradient (`'oversampling', true`), `mr.makeArbitraryGrad`
and `getBlock` compute the area from the samples on the raster centres only:

```matlab
grad.area=sum(grad.waveform(1:2:end))*system.gradRasterTime; % undo oversamping
```

The samples on the raster edges do not count. So `grad.area` is the area of the gradient
through the centre samples, but not of the gradient through the edge samples, and not of
the gradient through all samples that `waveforms_and_times` (and so the k-space
calculation) uses. The three areas agree when the gradient is linear across each raster
cell.

Since #236, an interpreter can get either the centre samples or the edge samples of an
oversampled gradient (#109). Is `grad.area` meant to be the area of the centre samples,
also for an interpreter that plays the edge samples?

**Example**

The triangle of 17 samples, from 0 to 4.05 mT/m and back, at 90 % of `maxSlew` =
100 T/m/s. Its peak is a centre sample, so the gradient is not linear across that raster
cell.

```matlab
sys = mr.opts('MaxSlew', 100, 'SlewUnit', 'T/m/s');
dt = sys.gradRasterTime;  % 10 us

step = 0.9 * sys.maxSlew * dt / 2;  % 90 % of maxSlew over half a raster
w = step * [1:9, 8:-1:1];           % 17 samples: centre, edge, centre, ..., centre

% the triangle starts and ends at 0
g = mr.makeArbitraryGrad('x', w, sys, 'oversampling', true, 'first', 0, 'last', 0);

w_all = g.waveform(:)';
e = [g.first, w_all(2:2:end), g.last];  % the gradient at the raster edges, t = 0, dt, ..., shape_dur

area_centre = g.area                                                     % sum(w_all(1:2:end)) * dt
area_edge = dt * (sum(e) - (e(1) + e(end)) / 2)                          % piecewise linear through the edge samples
area_all = trapz([0, g.tt(:)', g.shape_dur], [g.first, w_all, g.last])  % piecewise linear through all samples
```

| Area | 1/m | vs. `area_all` |
|---|---|---|
| `area_centre` (`g.area`) | 7.8553 | +1.2 % |
| `area_edge` | 7.6637 | −1.2 % |
| `area_all` | 7.7595 | |

`area_all` is always the mean of `area_centre` and `area_edge`. For a smooth gradient the
differences are smaller: for a half sine of 21 samples, `area_centre` is 1.0 % larger
than `area_edge`.

**Details**

- [`makeArbitraryGrad.m`, line 88](https://github.com/pulseq/pulseq/blob/c7469123c2f381f065986e6cc3a7d09730ed16ef/matlab/%2Bmr/makeArbitraryGrad.m#L88)
  and [`getBlock`, line 1390](https://github.com/pulseq/pulseq/blob/c7469123c2f381f065986e6cc3a7d09730ed16ef/matlab/%2Bmr/%40Sequence/Sequence.m#L1384-L1390):
  the area of the centre samples.
- [`waveforms_and_times`, lines 2023-2029](https://github.com/pulseq/pulseq/blob/c7469123c2f381f065986e6cc3a7d09730ed16ef/matlab/%2Bmr/%40Sequence/Sequence.m#L2023-L2029):
  the gradient piecewise linear through `[0 tt shape_dur]` and
  `[first waveform last]`, that is through all samples.
- A gradient made to match `g.area`, for example a rephaser with
  `mr.makeTrapezoid('x', 'Area', -g.area, ...)`, then does not cancel the area in the
  k-space calculation, or on an interpreter that plays the edge samples.

For a gradient on the regular raster, `sum(waveform) * gradRasterTime` also differs from
the area of the gradient piecewise linear through `first`, the samples and `last`. So
`area` may be meant as the area of the nominal samples in general. If that is the
intended definition, it could be documented for the oversampled case. Otherwise, the
area of all samples (`area_all`) would be consistent with `waveforms_and_times`.

pypulseq computes the area in the same way
([`make_arbitrary_grad.py`, line 119](https://github.com/pulseq/pypulseq/blob/f2c582bae13145b8ac71958726bc8b5a14bd1cfd/src/pypulseq/make_arbitrary_grad.py#L119),
[`Sequence/block.py`, line 429](https://github.com/pulseq/pypulseq/blob/f2c582bae13145b8ac71958726bc8b5a14bd1cfd/src/pypulseq/Sequence/block.py#L429)),
and gives the values above.

This was identified and the example generated by Claude, but I've reviewed the code
myself and the finding appears to be correct based on my review.
